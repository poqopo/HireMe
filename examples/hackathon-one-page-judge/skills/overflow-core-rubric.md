# Sui Overflow Core Rubric

Use this rubric when the review targets Sui Overflow.

## Weighted Criteria

### Product & UX - 20%

Judge whether the project feels usable, polished, and easy to understand.

High-scoring evidence:
- a clear user journey
- a demo judges can follow quickly
- polished screens or CLI flow
- before/after outcome proof
- error handling, onboarding, and result clarity

Low-scoring evidence:
- rough prototype with unclear flow
- mostly architecture screenshots
- no visible result
- user value requires a long explanation

### Real-World Application - 50%

This is the biggest category. Judge whether the project solves a meaningful problem with market relevance, long-term value, and ecosystem impact.

High-scoring evidence:
- a painful, specific user problem
- named users or operators
- a credible reason the solution matters beyond the hackathon
- a product loop that can be repeated
- evidence that Sui, Walrus, or the selected track makes the product more useful

Low-scoring evidence:
- novelty-only demo
- vague "AI/Web3" problem framing
- no path to repeated use
- sponsor technology added only for prize fit

### Technical Implementation - 20%

Judge whether the implementation is reliable, nontrivial, and meaningfully integrated with Sui.

High-scoring evidence:
- concrete contracts, PTBs, object IDs, blob IDs, APIs, SDK integrations, or testnet transactions
- end-to-end flow with clear failure boundaries
- meaningful Sui, Walrus, DeepBook, Seal, zkLogin, or Move usage
- security, privacy, reliability, and cost considerations

Low-scoring evidence:
- mock-only flow with no proof
- generic LLM wrapper
- storage/login/payment bolted on without affecting the product
- no technical artifact judges can inspect

### Presentation & Vision - 10%

Judge whether the one-pager tells a clear story and shows where the project goes next.

High-scoring evidence:
- one-sentence pitch is obvious
- demo proof is easy to find
- roadmap is specific and plausible
- vision connects to Sui ecosystem impact

Low-scoring evidence:
- dense feature list
- unclear target track
- no prize-facing story
- roadmap is generic or unrealistic

## Strong Overflow Project Pattern

Strong projects usually:
- solve meaningful problems
- have polished UX
- leverage Sui meaningfully
- demonstrate strong product thinking
- show long-term potential beyond the hackathon

Overflow rewards meaningful products and ecosystem impact, not just technical demos.

## Output Guidance For Overflow Reviews

After scoring, include:

- Differentiation to emphasize: compare the project against likely same-track project shapes, such as generic AI wrappers, storage-only demos, DeFi dashboards, payment flows, vault strategies, or analytics tools.
- Criteria fit analysis: explain how the current one-pager maps to Product & UX, Real-World Application, Technical Implementation, and Presentation & Vision.
- Refinement actions: state what should be moved earlier, what proof should be shown, and what language should be removed or replaced.
- Highest-leverage additions: list only additions that would plausibly move the weighted score, especially Real-World Application and Technical Implementation.
- Technical reality check: separate verified evidence from plausible but unproven claims.
- Past-winner pattern and shortlist likelihood: compare against prior Sui Overflow winner patterns and say what would make the project shortlist-ready.
- Demo order: give a judge-facing sequence that shows the product value before architecture detail.
- Judge objections to preempt: name the doubts judges may have and the proof needed to answer them.

The goal is not only to score the project. The goal is to help the team reshape the submission around the criteria that judges will actually use.
